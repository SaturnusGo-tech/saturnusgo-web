# Эксперимент оформления Falcon · 25 сентября 2026

Ветка: `experiment/glass-workspace`, отдельный worktree `.tms-glass-frontend`.
Первоначальный эксперимент проверен локально. 26 сентября 2026 пользователь одобрил публикацию: «Заливай на прод - я гляну». Релизная ветка: `release/glass-workspace-20260926`.

## Область изменений

- Общая оболочка: фон, парящий сайдбар и хедер; существующие пункты навигации и их поведение сохраняются.
- Репозиторий: дерево, строки кейсов, управление шириной, карточка кейса.
- Дашборд: оформление существующих метрик, графиков, фильтров, детализации и настройки виджетов.
- Бизнес-логика, контракты API, права и вычисления метрик не перерабатываются. Другие экраны оформляются только после принятия этого этапа.

## Включение и запуск

В релизной ветке оформление включено по умолчанию и добавляет `data-appearance="glass"` на корневой workspace. Явное `NEXT_PUBLIC_FALCON_GLASS_EXPERIMENT=false` возвращает прежнее оформление и ключ ширины репозитория. Значение применяется при запуске/сборке Next; после его изменения сервер нужно перезапустить. Исходная экспериментальная ветка сохраняет включение через `true`.

Из родительского каталога `SaturnusGo-Universe` запустить изолированный backend:

```sh
node output/falcon-glass-experiment-20260925/stand/tools/serve-demo.mjs
```

Из `.tms-glass-frontend` запустить frontend:

```sh
NEXT_PUBLIC_FALCON_GLASS_EXPERIMENT=true NEXT_PUBLIC_TMS_API_BASE=http://localhost:4142/api/v1 NEXT_PUBLIC_FALCON_MANAGED_AUTH=false node node_modules/next/dist/bin/next dev -H 127.0.0.1 -p 4542
```

Войти через `http://localhost:4142/demo-signin`; frontend работает на `http://localhost:4542`. Использовать `localhost` для обоих адресов, чтобы локальная cookie была доступна. Детали PostgreSQL, сессии и URL: [README стенда](../../output/falcon-glass-experiment-20260925/stand/README.md).

Стенд содержит **31 кейс, 6 прогонов, 3 сьюта**, два проекта, портфель, три дефекта и дашборд из десяти виджетов. Это записи, созданные через настоящий локальный API, а не числа, нарисованные в интерфейсе. Повторно запускать seed-скрипты в той же БД нельзя: они не полностью идемпотентны.

## Визуальные правила

- Светлая тема: выбранный `01-pearl-workspace.png`, жемчужный фон и единая светлая рабочая поверхность.
- Тёмная тема: уточнённый вариант 03, графитовые поверхности, холодные светлые оттенки фона; без выраженного фиолетового.
- Крупные полупрозрачные поверхности; обычные строки, описания и шаги не превращать в отдельные карточки.
- Единственный основной слой `backdrop-filter` находится на сайдбаре. Не добавлять blur каждому виджету или строке.
- Меню и всплывающие панели используют плотный `--glass-panel-strong`, чтобы текст под ними не мешал чтению.
- Общие цвета задаются в `presentation/workspace/appearance/glass.module.css`; все новые правила ограничиваются экспериментом. Общие деревья выбора в прогонах и сьютах не должны получать оформление репозитория.
- Ширина репозитория хранится отдельно: `tms.folders.width.glass.v1`; обычный ключ `tms.folders.width.v1` не изменяется. Начальная экспериментальная ширина 400 px, затем действуют сохранённое значение и существующие ограничения доступной ширины.

## Проверка перед просмотром пользователем

- Обе темы при 100% масштабе, окна 1280×800 и 1440×900; компактная навигация, прокрутка и длинные названия.
- Репозиторий: раскрытие папок, выбор кейса, изменение ширины, создание и перенос; сохранение контекста после навигации.
- Карточка: вкладки без обрезания и двойного индикатора, меню действий, редактор, вложения; клавиатурный фокус и Escape.
- Дашборд: переходы из метрик, вкладки, фильтры, меню периода, настройка, каталог и перестановка виджетов. Количества должны соответствовать API.
- Проверить отключённый флаг: прежнее оформление и прежняя сохранённая ширина. Проверить общие деревья в прогонах и сьютах на отсутствие новых рамок и отступов.
- `npm run typecheck`, `npm run architecture:tms`, `git diff --check`; для затронутого поведения использовать существующие тесты ширины репозитория, навигации карточки и детализации дашборда.

## Ограничения стенда

Backend использует отдельную локальную БД и блокирует внешние запросы. AI, фоновые jobs, внешние интеграции и облачные вложения здесь не проверяются. Управляемая облачная авторизация отключена; ссылки облачного профиля и админки могут отсутствовать из-за существующего gate, а не из-за редизайна. Локальная сессия хранится в закрытом файле стенда; её нельзя публиковать или переносить в репозиторий.

Следующие экраны и объём работ согласуются отдельно. Одобрение публикации относится к общей оболочке, репозиторию, карточке кейса и дашборду. Не распространять специфичное оформление этих экранов автоматически на прогоны, дефекты, интеграции, настройки или админку. Production собирается штатным скриптом с production API и авторизацией; конфигурация локального стенда в релиз не переносится.
